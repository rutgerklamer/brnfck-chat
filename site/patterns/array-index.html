Watch it run

The form “Fetch, carrying the value home” works on 21 cells; the named ones are “zero”, “index”, “out”, “count”, “item 0”, “carry”, “item 1”, “item 2”, “item 3”, “item 4” and “item 5”. Press Play, drag the step slider forwards and back, or change index i with the slider and edit the array:

There are no addresses. The program cannot say "go to cell i". It can only walk, and count the walk down: the index travels along with the pointer and loses 1 at every item.

In our form each item is three cells: a counter slot, the item, and a carry slot. Walking out, the counter is moved one item on and a 1 is left behind as a trail. At the item, the value is copied into the carry slot.

Walking back, the trail says "not home yet": each step clears one trail mark and moves the carry one item to the left. A zero cell before the array ends the walk.

The wiki form uses two cells per item and lays the whole trail first. Its fetch walks the trail once for every unit of the value, so its cost grows with index × value. Ours grows with the index only.

What it needs

  • Our form: a zero cell, the index, one more cell, then the array at three cells per item. The index is used up.
  • Wiki form: index, value or out, a temp, then head, two temps and the array at two cells per item.
  • The index must be inside the array. Any cell size.
Common mistakes
  • An index past the end: the walk goes on into whatever follows the array.
  • Forgetting that the walk costs time. Item 1000 is 1000 hops away, every time. The project cuts this to a few dozen with long hops: see Build toward a chatbot, lesson 7, "No addresses".

Where it is used

  • Build toward a chatbot, lesson 7, "No addresses", fetches from a table of 64 records with long and short hops.
  • The chat program avoids indexing where it can: a table whose index is known to be small becomes a decision tree in the program text (see table lookup as a decision tree).
